# 立项报告

## 一句话介绍

给本校「星火义务维修队」12 名队员用的「报修派单与配件台账」小站：谁接了单、修到哪一步、配件还剩多少，一屏看清。

## 内容主题

**主题定位**：校园义务维修队的报修工单流转与配件库存管理。

**垂直场景**：本校星火义务维修队每周三下午在大学生活动中心设摊，为师生免费维修小家电、台灯、风扇、插线板等。队内 12 名队员，分电工、焊工、综合三个组。当前痛点有三：一是报修靠微信群刷屏，工单容易漏接、重复接；二是维修进度不透明，送修人反复追问「修好没」；三是配件（电阻、电容、螺丝、焊锡、插头）用完了没人知道，采购靠临时想起。这是一个典型的「小团队工单流转 + 物料台账」处境，真实、具体、可验证。

**用模板的话回应条款**：这不是「校园服务平台」，也不是「维修管理系统」，而是「12 名队员、每周三下午、三类维修组、若干种配件」的具体处境。场景有真实的人（队员与送修师生）、真实的事（接单、维修、领料、归还）、真实的数据（工单号、故障类型、配件名称与数量、时间），符合「项目须长在具体场景里」的要求。

**为什么不做通用网站**：通用报修平台会取默认值——用户取「所有需要维修的人」，数据取「若干工单」，场景空着。本项目的每个字段都填上了别处抄不来的值：具体到星火维修队 12 人、每周三下午、电工/焊工/综合三组、电阻电容等真实配件。遮住项目名，换上任何同学的项目名，说明不成立，因此具备个性。

## 目标用户

**三类人，各自要干的事不同**：

1. **维修队队员（12 人，分三组）**：核心诉求是「别漏单、别重复接」。他们需要查看待接工单、抢单或派单、更新维修进度（待修 / 维修中 / 待配件 / 已修好）、登记领用的配件。这类用户是我日常直接接触的人，通过队内微信群和每周三摆摊现场即可触达。

2. **送修师生（约 30—50 人/学期）**：核心诉求是「知道修到哪一步了」。他们需要凭工单号查询进度，修好后收到通知，取件时确认签字。这类用户通过摆摊现场登记和活动中心公告二维码触达。

3. **队长（1 人，我本人）**：核心诉求是「统筹与盘点」。需要查看本周工单总量与完成率、各组工作量、配件库存余量，决定采购清单与下周排班。这是队内真实岗位，通过队内会议和当面沟通即可访问。

**访问方式**：全部是我够得着的人——队内微信群（12 人）、每周三摆摊现场、活动中心公告二维码、队长岗位本身。真实用户往往就是够得着的几十个人，这不是缺点，是数据来源的保证。数据来源就是这 12 名队员的真实接单记录与配件领用登记，而非凭空编造的假数据。

## 功能清单

功能按版本分层，单机完整的核心与多用户增强分开列，每个功能都能指出回应哪个痛点。

### 单机版本（必做，本地存储 + 支持登录）

- **登录**：区分「队员」「队长」两种角色，队员可接单与更新进度，队长可派单、盘点、导出。登录意味着用户数据与权限差异，是向网络版本迁移的准备。
- **工单登记**：录入送修人、联系方式、物品名称、故障描述、送修时间，自动生成工单号。回应「报修靠刷屏、容易漏」的痛点。
- **工单看板**：按状态分列（待接 / 维修中 / 待配件 / 已修好），显示工单号、物品、负责人、更新时间。回应「进度不透明」的痛点。
- **接单与进度更新**：队员接单后更新状态，每次变更留时间戳。回应「重复接单、责任不清」的痛点。
- **配件台账**：登记配件名称、规格、入库数量、领用数量、当前余量，领用时自动扣减。回应「配件用完了没人知道」的痛点。
- **我的工单**：队员查看自己接过的单与完成情况。
- **队长后台**：派单、查看全班工作量统计、导出本周工单与配件消耗清单。

### 多用户增强（网络版本，可选）

- **多人实时同步**工单状态，避免两名队员同时接同一单。
- **送修人自助查询**：凭工单号在页面查询进度，减少队员被追问。
- **配件库存预警**：余量低于阈值时页面高亮，提醒队长采购。
- **工作量排行**：队内激励，也便于学期末评优。

**单机与多用户的区分**：登录、工单登记、工单看板、接单与进度更新、配件台账、我的工单、队长后台属于单机可完成；实时同步、自助查询、库存预警、工作量排行涉及多用户操作，必须切后端。立项阶段明确区分，避免把多用户功能硬塞进单机版。

## 技术选型

- **存储方案**：单机版用 localStorage 存用户、工单、状态流转记录、配件台账；数据访问单独封装成 `store.js` 一层，界面只调用它的方法，不直接读写 localStorage。这是必须遵守的工程纪律：界面不直接碰数据，数据访问独立成层。
- **前端技术**：HTML + CSS + 原生 JavaScript（课程范围内），不引入框架充个性。技术栈不是个性的来源，场景和数据才是；这里是课堂，不是生产车间。
- **未来切后端**：把 `store.js` 换成调用 RESTful 接口的实现即可，界面层不动。做到这条，「切后端」就是换数据适配层的实现，而非重写应用；做不到，网络版本就不是升级，而是另起炉灶。
- **兼容性考虑**：单机阶段就把数据访问独立成层，为后端切换预留接口，避免后期重写。

## 里程碑

对着本班周程与检查点切，每段留可运行增量：

- **第 2 周**：立项报告 + 登录页跑通（本地假用户），能进主界面。可运行增量 = 登录流程。
- **第 4 周**：工单登记 + 工单看板可运行，数据存 localStorage，单人可用。可运行增量 = 登记与看板。
- **第 6 周**：接单与进度更新 + 配件台账 + 我的工单完成，队长后台可用。可运行增量 = 流转与台账。
- **第 8 周**：整理数据层为独立 `store.js`，界面与数据彻底分离。可运行增量 = 数据层重构。
- **第 10 周**：如时间允许，接入后端实现多用户实时同步与库存预警；否则交单机完整版。可运行增量 = 后端切换或单机收尾。

## 风险与对策

风险写真实的，不写「没有风险」。

- **数据拿不到怎么办**：真实工单依赖维修队实际运行。对策：先用上周三摆摊的真实工单（约 15 单）录入作为种子，页面标注「示例数据」；若队内暂未同意，则先自建 10 条模拟工单验证流程，再替换为真实数据。
- **做不完先砍什么**：功能砍序为「工作量排行 → 库存预警 → 配件台账 → 自助查询」；工单登记 + 工单看板 + 接单与进度更新 + 登录为核心，必须保住。每段留可运行增量，砍功能不砍可运行性。
- **多人同时接单冲突**：单机版各存各的会打架。对策：单机版明确标注「单人视角」，把实时同步整体推迟到网络版本，不在单机阶段硬凑。
- **配件名称不统一**：队员各写各的（「电阻」vs「1k 电阻」），台账会乱。对策：建立配件分类字典（名称 + 规格 + 单位），领用时从字典选，不允许自由填写。
- **数据形态单一**：若只记物品名，数据不够多样。对策：确保至少三类字段互相配合（人员、时间、配件、金额），如下表。

# 从生成代码到理解代码

初版使用 AI 辅助生成。本文件是学习建议，不代表学生已完成学习或独立实现。

## 第一轮：一张图鉴卡片

打开 `index.html`、`js/data/catalog.js` 和 `js/ui/app.js`。从 `card()` 开始，找出中文名、图片、属性、能力总和怎样变成 HTML。修改一处卡片排版，解释为什么修改 CSS 而不改数据。

自测：`item.types.map(typePill).join('')` 分别做了什么？为什么输出用户昵称前需要 `escape()`？

## 第二轮：筛选和排序

阅读 `filtered()`、`updateGrid()` 以及 input/change 事件。先用三条数据手算筛选结果，再打开页面验证。尝试增加一个自己理解的排序方式。

自测：为什么 `sort()` 有时会修改原数组？这里的筛选结果为什么可以排序？为什么搜索时不重建整个页面？

## 第三轮：收藏和本地登录

阅读 `store.js` 的 `read()`、`save()`、`login()`、`toggleFavorite()`。用 leaf 收藏皮卡丘，再换 blue 查看，刷新后再登录 leaf。

自测：个人记录怎样按用户 ID 分开？页面为什么调用异步接口？本地密码为什么不能作为正式认证方案？

## 第四轮：双属性倍率

阅读 `rules.js` 的 `multiplier()`。先用火→草、电→地面、冰→草+飞行三组属性例子手算，再到实验室选择真实图鉴目标，例如岩石→喷火龙（火／飞行），核对 2 × 2 = 4。图鉴目标的防御属性来自资料，不能为了凑例子手动修改。把 `reduce()` 改写成自己理解的 for 循环，并运行测试验证等价。

自测：2×2、0.5×0.5、2×0 分别是多少？属性倍率为什么不等于实际伤害？

## 第五轮：队伍与备份

阅读 `saveTeam()`、`importProfile()`、队伍页面的 `team()` 和 `analysisHtml()`。尝试重复成员、七个成员、错误备份文件，观察错误处理。

自测：为什么要先校验全部导入内容再保存？为什么导出文件不包含密码？修改已保存队伍与新建队伍如何区分？

## 第六轮：预算、参考队伍与公平比较

阅读 `rules.js` 中预算和队伍统计函数、`js/data/challenges.js`，再追踪页面添加成员、`saveTeam()`、`importProfile()` 怎样使用同一个预算规则。选三位成员，先手算各自六项基础能力总和，再用 `reduce()` 求队伍成本和剩余预算。分别尝试恰好达到 3000 点与超过 3000 点的组合，观察反馈。

比较当前编辑队伍和一支参考队伍，手算一项能力的平均值、一个属性的成员数，以及一个攻击属性下的弱点人数。尝试不同成员数量，解释为什么合计值与人数需要一起看。参考队伍属于作者编排的只读内容，个人队伍属于登录用户的本地记录；修改个人队伍时不应改写参考内容。

自测：为什么添加、保存和导入不能各自写一个预算数字？`reduce()` 的初始值为什么是 0？空队伍的平均值怎样避免除以 0？旧超预算队伍为什么保留，而含超预算队伍的新备份导入需要整次拒绝？为什么这些指标不能推出真实战斗胜率？

## 第七轮：说明与单一配队任务

先展开页面的新手说明，用自己的话解释六项基础能力各描述什么，为什么基础值不等于某个等级下的实际能力，以及弱点、抵抗、免疫对应哪些倍率。注意本项目抵抗人数包含免疫成员。用一个双属性例子手算电属性攻击倍率，再查看页面中的电弱点人数。

阅读配队任务的纯计算函数与页面渲染：任务只观察当前编辑队伍，条件是“6 位不重复成员、总成本不超过 3000 点、电弱点人数不超过 2 位”。先准备一个满足条件的组合，再各改变一个条件，观察完成提示怎样变化。成员不足时，即使另外两项已满足，也不能认为整个任务完成。

自测：为什么三项条件需要同时满足？如何用 `Set` 判断成员不重复、用 `filter()` 数电弱点成员？电属性倍率为 1、0.5、0 时分别算不算弱点？载入一支参考队伍后为什么需要重新检查？为什么任务结果只由当前队伍计算，不需要写入 localStorage？任务完成为什么不会自动保存队伍、产生成绩或决定对战胜负？

尝试调整一段折叠说明，使不熟悉宝可梦的同学更容易读懂；只有实际收到反馈后，才把反馈和改进过程写入项目日志。这一轮仍是学习建议，不表示已经完成学习或试玩。

## 第八轮：把计算结果变成属性实验

先读 [开发说明](开发说明.md) 的实验室流程，再看 `rules.js` 的 `typeExperiment()`：输入是一个攻击属性、目标的防御属性数组和属性表，输出包含逐项倍率、总倍率与结果分类。它不碰页面。分别用岩石→喷火龙、火→喷火龙、一般→皮卡丘、电→小拳石手算弱点、抵抗、普通效果和免疫四种结果，特别检查 0 是否优先归为免疫。

追踪 `app.js` 中攻击选择、目标编号与是否已发射的临时状态，找出“选择 → 准备 → 发射 → 结果”的顺序。更换角色后，说明为什么必须同时更新图片、防御属性和准备提示。再阅读 `lab-effects.js`，区分“算出了什么”与“怎样让人看见”，检查取消和减少动态效果的处理，不要把倍率写进动效模块。

自测：攻击角色可能有两个属性，为什么本次攻击仍只选一种？为什么双属性目标要相乘而不是相加？为什么免疫的结果仍能用文字读到？连续发射或中途切换选择时，旧动效为什么需要取消？实验发射、五题练习、配队任务分别有哪些内容会保存？

亲自完成一项能解释的小改动，例如修改一条结果台词或一处动效时长，说明改动位置、实际观察和是否影响计算。按照 [课堂汇报提纲](课堂汇报提纲.md) 练习一次 2 分钟演示，再记录自己还答不出的一个问题，不预填“已掌握”。

## 每次提交写真实记录

建议在项目日志新增一段：这次读了哪个函数；自己改了什么；如何验证；还有哪个问题不懂。不要把 AI 生成的说明直接当作个人反思，不要伪造试玩人数或学习完成情况。

运行 `node --test tests/*.test.cjs` 可以检查关键规则，但通过测试不等于本人理解代码。
